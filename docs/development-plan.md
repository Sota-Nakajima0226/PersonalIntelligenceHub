# 開発計画（v0.3 叩き台）

仕様は [spec.md](./spec.md) を参照。

## 進め方の原則

- 週数時間のペースを前提に、1つのマイルストーンを2〜6週で終えられる大きさに保つ。
- CursorでのAI駆動開発を前提とし、実装の前に設計書を整備する。設計書はコードと同じリポジトリで管理し、コードの変更時に同時に更新する。
- 詳細な設計はMVPの範囲に限定し、P2以降の機能は必要になった段階で設計する。
- 最小の機能を一通り動かした段階で、早めにEC2へデプロイする。インフラの学習はこの段階から始める。
- 規約はCursorのルールに書くだけでなく、リンター・フォーマッター・型チェックで機械的に強制する。
- 各マイルストーンの終わりに「何を学んだか・なぜその設計にしたか」を短くメモしておく（転職時の説明材料になる）。

## マイルストーン

### M0：準備（1〜2週）

全体仕様の確定：

- [ ] `docs/spec.md`（コンセプト・機能要件・技術スタック・システム構成図など）をレビューし、v1.0 として確定する
- [ ] 初期に購読するフィードとキーワード、「自分の興味」の記述を決める

Gitリポジトリ（公開）：

- [ ] ホームディレクトリに誤って作成された Git リポジトリ（`~/.git`）を確認・削除する
- [ ] プロジェクトのディレクトリで `git init`
- [ ] 公開前の確認
  - [ ] `.gitignore`（`.env`、`config/sources.yaml`、`_my_docs/` などを除外）
  - [ ] `.env.example`、`config/sources.example.yaml` を用意する（M1で作成するものは M1 で追加）
  - [ ] ライセンスを決める（例：MIT）
- [ ] README（概要、システム構成図、技術スタック、ドキュメントへのリンク）
- [ ] GitHub に公開リポジトリを作成し、初回 push（`gh repo create` または GitHub の画面）
- [ ] GitHub の secret scanning と push protection を有効にする

AI駆動開発の基盤：

- [ ] `AGENTS.md` の初版（プロジェクト概要、設計書の場所、技術スタック、予定するディレクトリ構成、禁止事項）

AWS：

- [ ] AWSアカウントの安全設定
  - [ ] ルートユーザーにMFAを設定し、普段は使わない
  - [ ] 作業用のIAM Identity Center ユーザー（またはIAMユーザー）を作成し、MFAを設定
  - [ ] AWS Budgets で月2,500円の予算通知を設定
  - [ ] 利用リージョンを東京（ap-northeast-1）に決める

**完了条件**：全体仕様が確定し、公開リポジトリに `docs/`・README・`AGENTS.md` がそろっている。AWSアカウントが安全に使える状態になっている。

### M0.5：設計（2〜3週）

設計書の構成は [spec.md の 10章](./spec.md#10-設計ドキュメント構成) を参照。

- [ ] `docs/design/database.md`：ER図、テーブル定義、記事の状態遷移
- [ ] `docs/design/api.md`：MVPのエンドポイント、リクエスト・レスポンス、エラー形式、認証方式
- [ ] `docs/design/screens.md`：画面一覧、画面遷移図、各画面の要素と操作
- [ ] `docs/design/ai-processing.md`：プロンプト、出力JSONスキーマ、カテゴリ一覧、関連度の基準
- [ ] 画面モック：ダミーデータで動く React の画面（一覧・詳細・保存済み・設定）を作り、スマホ実機で操作感を確認する
- [ ] モックで見つかった問題を設計書に反映する

**完了条件**：MVPのDB・API・画面・AI処理について、AIに実装を依頼できる粒度の設計書がそろい、モックで画面の操作感を確認済み。

### M1：雛形を作り、最小のアプリをEC2に載せる（4〜6週）

開発基盤：

- [ ] リポジトリの雛形（`frontend/` `backend/` `infra/` `docker-compose.yml`）。M0.5のモックを `frontend/` に取り込む
- [ ] ローカルで PostgreSQL・FastAPI・React が Docker Compose で起動する
- [ ] リンター・フォーマッター・型チェックの設定（Python：ruff + mypy または pyright、フロントエンド：ESLint + Prettier）と pre-commit
- [ ] Cursorの規約ファイル（`.cursor/rules/`）を作成：`backend-python`、`frontend-react`、`database`、`docs-sync`
- [ ] テスト用のフィードのサンプルファイルと、LLMのダミー実装の置き場所を決める

機能：

- [ ] DBスキーマ（`sources` `items` `fetch_logs` `jobs`）と Alembic マイグレーション
- [ ] worker：`sources sync` コマンド（`config/sources.yaml` をDBに同期）
- [ ] worker：`fetch` `filter` コマンド（URL正規化・重複排除・キーワード絞り込み、情報源・件数の指定、ドライラン）
- [ ] API：`GET /api/items`、`GET /api/items/{id}`
- [ ] 画面：モックをAPIに接続し、記事一覧と詳細を表示する
- [ ] ログイン（1ユーザー用パスワード認証）

デプロイ：

- [ ] t4g.micro を起動、セキュリティグループ設定（SSHは自分のIPのみ、80/443を公開）
- [ ] スワップ設定、Docker のインストール
- [ ] ドメイン取得・DNS設定
- [ ] Nginx + Let's Encrypt でHTTPS化
- [ ] cron で `fetch` と `filter` を1日2回実行
- [ ] PostgreSQLの日次バックアップ
- [ ] `docs/design/infrastructure.md` にAWS構成・デプロイ手順・復旧手順を記録

**完了条件**：スマホから自分のドメインにHTTPSでアクセスし、ログイン後に毎日更新される記事一覧が見られる。手動でもコマンドで取得を実行できる。

### M2：AIによる要約・分類（3〜4週）

- [ ] LLMクライアントを1モジュールに集約（モデル差し替え可能な形）
- [ ] 候補モデル2〜3種で、実際の記事20件程度の要約品質と費用を比較し、採用モデルを決める
- [ ] `analyze` コマンド：要約・カテゴリ・タグ・関連度の生成、Pydanticによる出力検証
- [ ] `run` コマンド（取得 → 絞り込み → AI処理）に cron を切り替える
- [ ] 1日の処理件数上限、再試行回数上限
- [ ] `llm_usage` への記録と `GET /api/stats/usage`
- [ ] 画面に要約・タグ・関連度を表示、関連度順の並び替え

**完了条件**：毎朝、日本語要約付きの記事一覧が自動で更新され、AIの月額推定費用を画面で確認できる。

### M3：毎日使える状態にする（3〜4週）

- [ ] 既読・保存・興味なし（`item_actions`）
- [ ] カテゴリ・情報源・未読/保存済みでの絞り込み
- [ ] 設定画面の「今すぐ取得」ボタン（`POST /api/jobs/fetch`）
- [ ] 下部ナビゲーション（ホーム / 保存済み / 設定）などスマホ向けUIの改善
- [ ] PWA対応（マニフェスト、アイコン、ホーム画面への追加）
- [ ] 1〜2週間実際に使い、不満点を洗い出して改善

**完了条件**：1週間、他の情報収集手段を使わずにこのアプリだけで情報収集ができる。

## AI駆動開発の基盤整備

Cursorに渡す前提情報は、一度に作り込まず、実際のコードに合わせて段階的に整備する。

| タイミング | 整備するもの | 内容 |
|---|---|---|
| M0 | `AGENTS.md` | プロジェクト概要、設計書の場所、技術スタック、ディレクトリ構成、よく使うコマンド、禁止事項（秘密情報のコミット禁止など） |
| M1の開始時 | `.cursor/rules/*.mdc` | 領域ごとの規約。対象ファイルのパターンで自動適用する |
| M1の開始時 | リンター・フォーマッター・型チェック・pre-commit | ルールを機械的に強制する |
| 同じ作業を2〜3回繰り返したとき | `.cursor/skills/*/SKILL.md` | 繰り返し発生する作業の手順 |

想定するファイル：

```
AGENTS.md                              # 全体の前提（常に参照される）
.cursor/rules/
  backend-python.mdc                   # backend/**：型ヒント、SQLAlchemy 2.0 の書き方、層の分け方、pytest
  frontend-react.mdc                   # frontend/**：TypeScript strict、コンポーネント粒度、Tailwind、モバイルファースト
  database.mdc                         # マイグレーション手順、命名規則
  docs-sync.mdc                        # DB・API・画面を変更したら設計書も更新する
.cursor/skills/
  add-api-endpoint/SKILL.md            # 設計書 → スキーマ → ルーター → テスト
  add-db-migration/SKILL.md            # モデル変更 → Alembic → 設計書の更新
  add-feed-source/SKILL.md             # 新しい情報源の追加
  deploy/SKILL.md                      # EC2へのデプロイ（M1後半）
```

## リスクと対策

| リスク | 対策 |
|---|---|
| t4g.micro のメモリ不足 | スワップ設定。worker は常駐させない。PostgreSQLのメモリ設定を控えめにする。不足が続けば t4g.small へ変更（予算を再検討） |
| AI費用の想定外の増加 | 1日の処理件数上限、再試行上限、利用量の記録と予算通知の二重管理 |
| arXiv の件数が多すぎる | カテゴリを絞る、キーワードによる事前絞り込み、関連度の低い候補は処理しない |
| フィードの取りこぼし | 1日2回取得する。取得件数の推移を `fetch_logs` で確認し、必要なら頻度を上げる |
| 開発が長期化して途中で止まる | マイルストーンごとに「使える状態」で区切る。M1の時点で自分が毎日見るものにする |
| 設計書とコードの乖離 | `docs-sync` ルールで更新を促す。実装後のAPI仕様は OpenAPI を正とする |
| フィードの仕様変更・取得失敗 | `fetch_logs` でエラーを記録し、画面またはログで検知できるようにする |
